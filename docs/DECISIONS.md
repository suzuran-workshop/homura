# Suzuran Cloud Decisions

> 设计背后的历史原因，防止架构漂移

## 2026-08-02: 从低代码平台转向 AI 原生应用平台

### 背景

Suzuran Cloud 最初定位为多租户低代码平台，已建设：
- 拖拽表单设计器（FormDesigner、widget_library）
- 动态表单 JSONB schema 渲染
- 可视化工作流引擎
- 报表设计器

### 决策

放弃低代码方向，转向 AI 原生应用平台。具体：
- 只保留多租户四件套（org/user/bond/dept）+ JWT + tenant 中间件
- 移除所有低代码资产（拖拽设计器、工作流引擎、报表设计器、动态表单）
- 新建 MCP Server、应用运行时、OAuth IdP、Skill/MCP 契约

### 原因

1. **Vibe Coding 的兴起**：Agent 生成生产级代码的速度和质量已经超越拖拽设计器。低代码的"降低门槛"优势在 AI 时代不再稀缺。

2. **低代码的天花板**：拖拽产出的应用受限于平台 DSL，而 Agent 写出的代码可以任意复杂。低代码平台的终局是被 Vibe Coding 吞掉。

3. **平台价值的转移**：平台的价值从"低代码编辑器"变成"AI 原生应用运行时 + 数据共享层 + 契约发布层"。Agent 需要的是严格契约（Skill/MCP）和托管运行时，不是拖拽界面。

4. **数据共享的需求**：应用间需要共享数据（公共基础数据 + 跨领域业务数据），低代码平台的 DSL 难以表达这种复杂的共享关系。MCP 契约更灵活。

### 后果

- **短期**：大量代码被删除（拖拽设计器、工作流引擎等），需要重建 MCP/运行时/OAuth
- **长期**：平台定位更清晰（AI 原生），技术栈更现代化（MCP + WebAuthn），竞争力更强
- **风险**：MCP 生态尚早期，应用运行时方案（Docker/gVisor/Firecracker）需要评估

### 替代方案

**保留低代码方向**：继续演进拖拽设计器和工作流引擎。放弃原因：Vibe Coding 的冲击太大，低代码的长期生存空间存疑。

**混合模式**：同时支持低代码和 AI 原生。放弃原因：两条路线的技术栈差异太大，维护成本高，不如聚焦。

## 2026-08-02: 应用采用托管运行形态

### 背景

Agent 开发的应用在平台上的运行形态有三种选择：
1. 平台托管运行（应用跑在平台进程/容器里）
2. 独立服务 + MCP 接入（应用跑在外部，通过 MCP 访问数据）
3. Agent 即时生成的脚本/工作流（应用不是常驻服务）

### 决策

选择方案 1：平台托管运行。

### 原因

1. **强一致性**：应用跑在平台内，数据共享走进程内调用（或本地网络），延迟低、一致性强。独立服务方案需要跨网络调用 MCP，延迟和故障风险更高。

2. **统一管理**：平台管理应用的生命周期（启停、升级、迁移、销毁），租户管理员可以在一个界面看到所有应用的状态。独立服务方案下，应用散落在各处，管理成本高。

3. **资源配额**：平台可以给每个应用分配 CPU/内存/数据库连接配额，超出则限流。独立服务方案下，平台无法控制外部应用的资源使用。

4. **安全隔离**：平台可以用沙箱（namespace、cgroup、seccomp）隔离应用，防止应用互相攻击或逃逸。独立服务方案下，隔离由应用自己负责，安全风险高。

5. **计费基础**：托管运行天然有资源使用数据（CPU 时间、内存峰值、数据库连接数），可以作为计费依据。独立服务方案需要应用自己上报使用量，容易作弊。

### 后果

- 平台需要建设应用运行时（沙箱隔离、进程管理、资源配额）
- 应用必须遵循平台的运行时接口（如何启动、如何注册路由、如何接收请求）
- 平台复杂度增加（要管理应用生命周期）

### 替代方案

**独立服务 + MCP**：更灵活，应用可以用任意语言/框架，部署在任意位置。放弃原因：数据共享延迟高、管理分散、安全风险大。

**即时脚本**：最 AI 原生，应用不是常驻服务，而是 Agent 按需生成并执行。放弃原因：工程上太难（沙箱隔离、超时、状态管理、成本），不适合长期运行的应用。

## 2026-08-02: 平台自建 OAuth IdP

### 背景

WebAuthn OAuth 的实现有两种选择：
1. 平台自建 IdP（自己实现 WebAuthn ceremony + 钉钉 OAuth + OAuth2 端点）
2. 集成第三方 IdP（Keycloak/Authentik 等）

### 决策

选择方案 1：平台自建 IdP。

### 原因

1. **轻依赖**：Keycloak 是 Java 巨兽（需要 JVM、大量内存、复杂的配置），Authentik 也不轻。Suzuran Cloud 是 Go 项目，引入重型 IdP 会增加运维成本。

2. **完全自控**：自建 IdP 可以完全控制鉴权流程、token 格式、权限模型。第三方 IdP 的权限模型可能和平台的多租户模型不匹配，需要做适配层。

3. **WebAuthn 成熟**：Go 生态有成熟的 WebAuthn 库（`go-webauthn/webauthn`），实现 ceremony 不难。钉钉 OAuth 已经有 SDK 雏形，补全即可。

4. **OAuth2 标准**：OAuth2 协议本身不复杂，自己实现 authorization_code 流程、token 签发、refresh token 管理是可行的。

### 后果

- 平台需要实现 WebAuthn ceremony（注册/登录、credential 存储）
- 平台需要实现 OAuth2 端点（`/oauth/authorize`、`/oauth/token`、`/oauth/revoke`）
- 平台需要实现 token 管理（JWT 签发、refresh token、登出黑名单）
- 平台需要维护 IdP 的安全性和合规性

### 替代方案

**集成 Keycloak/Authentik**：鉴权成熟快，自带 WebAuthn + OIDC + SAML 全家桶。放弃原因：依赖太重（Java/Python 进程、复杂配置、高内存占用），与 Go 项目的轻量风格不符。

## 2026-08-02: 多租户采用共享数据库 + org_id 字段隔离

### 背景

多租户数据隔离有三种主流方案：
1. 独立数据库（每个租户一个数据库）
2. 独立 schema（同一数据库，每个租户一个 schema）
3. 共享数据库 + org_id 字段（所有租户共用表，用 org_id 字段区分）

### 决策

选择方案 3：共享数据库 + org_id 字段隔离。

### 原因

1. **简单**：不需要管理多个数据库或 schema，迁移和备份都更简单。

2. **跨租户查询**：平台管理端（服务商）需要跨租户查询数据（如"查看所有租户的应用列表"），共享数据库天然支持。

3. **成本**：独立数据库/schema 方案的数据库连接数和存储成本更高。

4. **已有基座**：现有代码已经实现了 org_id 字段隔离（`OrgUserBond` + tenant 中间件），延续即可。

### 后果

- 所有表必须有 `org_id` 字段（除全局表如 `users`）
- 所有查询必须加 `WHERE org_id = ?`，遗漏会导致数据泄露
- 需要代码审查和测试保证隔离正确性

### 替代方案

**独立数据库**：隔离性最强，但管理复杂、成本高。放弃原因：租户数量预期不会太大（企业级 SaaS），共享数据库足够。

**独立 schema**：隔离性中等，需要动态切换 schema。放弃原因：GORM 对多 schema 的支持不完善，容易出 bug。

## 2026-08-04: SDK 采用零依赖 Node.js 原生方案

### 背景

Agent 开发应用需要一个 SDK 来接入平台。SDK 的技术选型有三种：
1. 零依赖（Node.js 原生 `http` 模块）
2. 轻量框架（Express/Koa）
3. 全功能框架（NestJS/Fastify）

### 决策

选择方案 1：零依赖，只用 Node.js 内置模块。

### 原因

1. **最小化冲突**：Agent 写的应用可能依赖各种库，SDK 如果引入 Express/Koa，可能和应用的依赖冲突。零依赖意味着 SDK 不会和应用打架。

2. **够用了**：MCP 调用就是一个 `fetch()` 调 JSON-RPC 2.0，HTTP 路由用原生 `http.createServer()` 加几行路径匹配就够。不需要框架的中间件体系。

3. **安装快**：`npm install @suzuran/sdk` 零网络请求（除了 SDK 本身），Agent 开发的应用镜像构建更快。

4. **TypeScript 优先**：输出 `.d.ts` 声明文件，Agent 拿到完整类型提示，但不强制应用用 TypeScript。

### 后果

- SDK 功能范围有限（路由、MCP 客户端、生命周期），不提供数据库 ORM、模板引擎等
- 需要 Agent 自己处理复杂的 HTTP 场景（文件上传、WebSocket 等）
- ESM-only 输出，不支持 CommonJS `require()`

### 替代方案

**Express/Koa**：更丰富的中间件生态。放弃原因：和应用依赖冲突风险大，SDK 应该尽量透明。

**NestJS/Fastify**：性能更好、功能更全。放弃原因：太重，Agent 写个简单的 CRUD 应用不需要学一个框架。

## 2026-08-04: OAUTH_TOKEN 通过部署链路注入容器

### 背景

应用运行在容器里需要调用 MCP Server，MCP Server 要求 OAuth token 鉴权。token 如何到达容器？
1. 部署时从调用者的 Authorization header 提取，注入容器环境变量
2. 平台为每个应用签发长期 service token
3. 应用自己实现 OAuth 流程获取 token

### 决策

选择方案 1：部署时从调用者提取 Bearer token，通过 Handler→Service→Runtime 链路注入容器。

### 原因

1. **最小改动**：不需要新建 token 签发机制，直接复用现有的 OAuth token。

2. **安全可追溯**：token 有 15 分钟过期时间，审计日志记录的是部署者的身份，不是某个匿名 service account。

3. **不污染数据模型**：在 `Application` model 上用 `gorm:"-"` 标记为不持久化字段，不写数据库，只在部署时短暂传递。

### 后果

- 每次部署/重启需要前端传 Bearer token（已有，无需额外工作）
- token 15 分钟后过期，长期运行的应用需要 token 刷新机制（待建设）
- 不能离线部署（需要有效的 OAuth session）

### 替代方案

**平台签发 service token**：应用有自己独立的长期 token。放弃原因：需要新建 token 签发/管理/轮换机制，复杂度高，等应用生态成熟后再考虑。

**应用自登录**：应用启动时自己走 OAuth 流程。放弃原因：应用不应该知道登录凭据，违反最小权限原则。

## 2026-08-13: 流程引擎作为平台级能力（而非应用自建）

### 背景

6 个应用场景（课程管理、教师考核、行政办公、学生关爱、用餐、校园监控）中 5 个需要审批/流程能力——行政审批甚至有 5 种不同审批流，含树状父子流程。流程能力是 SaaS 应用的核心环节。问题：流程引擎该由基座提供，还是各应用自建？

### 决策

流程引擎作为**平台级能力**实现，通过 MCP 工具（`workflow.*`）暴露给所有应用。流程定义是 JSON，应用通过 SDK + MCP 定义/启动/审批流程，状态持久化在平台 PostgreSQL（`org_id` 隔离）。

### 原因

1. **避免重复劳动**：5/6 场景需要流程，每个应用自建引擎是巨大浪费且能力不一致。

2. **复用既有管道**：平台已有 MCP 鉴权/限流/审计管道（`WrapToolHandler`）和 `NotificationService.SendApprovalNotification` 桩，流程引擎直接接入即可。

3. **不违反 PRD 约束**：PRD 禁止的是"可视化流程编辑器"（低代码拖拽），而本引擎是 JSON 定义 + API 驱动的程序化引擎，Agent 通过 MCP 调用，完全符合 AI 原生定位。

4. **架构一致**：流程状态存平台 DB，受 `org_id` 隔离，遵循"应用只用 MCP 访问数据"的硬约束。

### 后果

- 新增 3 张表（`workflow_definitions`/`workflow_instances`/`workflow_tasks`）+ 11 个 MCP 工具
- 契约升至 v1.1.0（向后兼容新增）
- v1 步骤类型：start/approval/condition/end，指派：user/role，条件评估手写轻量表达式
- 后续可扩展：超时/SLA 自动升级、并行审批、子流程

### 替代方案

**各应用自建流程**：每个应用用 SDK 自己实现状态机。放弃原因：重复劳动、能力碎片化、审批通知无法跨应用统一。

**部署为独立应用**：把流程引擎作为一个普通 Suzuran 应用部署，其他应用通过代理调用。放弃原因：受 MCP 工具能力上限限制，无法实现跨租户审计、统一通知、平台级权限控制。
